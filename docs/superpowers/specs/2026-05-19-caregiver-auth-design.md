# Caregiver sharing & authentication — design

**Status:** Draft, pending implementation plan
**Date:** 2026-05-19
**Author:** brainstormed with Claude

## 1. Purpose

Today babyone is a single-user app: there is no concept of identity, `/api/baby` returns a hardcoded name, and every API route is open. This spec adds **authentication and multi-caregiver access for a single household** so that two or more caregivers (e.g. partners) can each sign in from their own device, log records, and see who logged what.

This is the foundation for several follow-on features (rate-limiting `/api/chat` per user, per-device push subscriptions for reminders). It is explicitly **not** a multi-tenant rewrite — babyone remains a single-household app.

## 2. Scope

### In scope
- Email + password sign-in for caregivers, hand-rolled over `@node-rs/argon2` + Hono cookie helpers.
- Server-side sessions stored in SQLite; opaque session ID in an HttpOnly cookie.
- One-time, 24-hour invite codes generated by any signed-in user to add new caregivers.
- A `user_id` column on `records` so the UI can show "logged by Calvin · 12 min ago".
- Auth middleware that gates every `/api/*` route except `/api/auth/login`, `/api/auth/signup`, and `/api/health`.
- A first-run bootstrap that creates the admin user from environment variables and fails loud if they are missing.
- A login page, a signup page (consumes invite codes), and an "Invite caregiver" panel in the sidebar.
- Vitest-based server and client tests for the auth surface.

### Explicit non-goals (YAGNI)
- Public signup, multi-household tenancy, `household_id` column.
- Email verification, password-reset emails, magic links, OAuth, MFA, passkeys.
- Roles (admin / caregiver / read-only). Everyone signed in is equal.
- Sliding session renewal, "active sessions" management UI, self-service account deletion.
- Audit log beyond `records.user_id`.
- Attributing chat messages to a specific user — household chat reads as a shared log.
- Per-user push subscriptions — belongs to the *Push reminders* feature.
- CSRF double-submit tokens — `SameSite=Lax` + `Origin` header check is sufficient given our shape.
- Distributed rate limiting — in-memory `Map` is fine for a single-instance Fly app.
- Playwright E2E — to be added in its own pass once multiple features span the auth boundary.

## 3. Architecture

```
server/
├── src/
│   ├── auth/                  ← NEW
│   │   ├── passwords.ts       hash(), verify() via @node-rs/argon2
│   │   ├── sessions.ts        create/lookup/revoke session rows
│   │   ├── invites.ts         generate/consume one-time codes
│   │   ├── middleware.ts      originGuard() + requireAuth() Hono middleware
│   │   └── routes.ts          /api/auth/* + /api/invites
│   ├── db.ts                  +users, sessions, invites tables; +user_id on records
│   ├── index.ts               wire requireAuth onto /api/* (after mounting login/signup/health)
│   └── seed.ts                +bootstrap first admin if no users exist; backfill records.user_id
└── package.json               +@node-rs/argon2

client/
├── src/
│   ├── auth/                  ← NEW
│   │   ├── useAuth.ts         useMe() hook + login/logout/signup helpers
│   │   ├── LoginPage.tsx
│   │   ├── SignupPage.tsx     reads ?code= from URL
│   │   └── InvitePanel.tsx    "Invite caregiver" → copyable link
│   ├── api.ts                 +login(), logout(), me(), createInvite(); fetch with credentials:'include'
│   ├── queries.ts             +useMe(); existing queries gain enabled: !!me.data
│   └── App.tsx                AuthGate: show LoginPage when me errors, app otherwise
```

### Invariants enforced by this design
1. Every `/api/*` route except `/api/auth/login`, `/api/auth/signup`, and `/api/health` requires a valid session.
2. Every row in `records` has a `user_id` after migration. New inserts read `user_id` from the session — **never** from the request body.
3. Sessions live in SQLite. No JWT. Logout = DELETE the session row.
4. There is exactly one household. Adding multi-tenancy later means adding a `household_id` column — we will not pre-design for it.

## 4. Data model

Three new tables and one new column. Everything additive; existing data stays valid.

```sql
CREATE TABLE users (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  email           TEXT NOT NULL UNIQUE COLLATE NOCASE,
  password_hash   TEXT NOT NULL,           -- argon2id encoded string
  display_name    TEXT NOT NULL,           -- "Calvin"; shown on records
  created_at      TEXT NOT NULL            -- ISO timestamp
);

CREATE TABLE sessions (
  id              TEXT PRIMARY KEY,        -- 32 random bytes, base64url
  user_id         INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at      TEXT NOT NULL,
  expires_at      TEXT NOT NULL,           -- created_at + 30d
  user_agent      TEXT NOT NULL DEFAULT ''
);
CREATE INDEX idx_sessions_user ON sessions(user_id);

CREATE TABLE invites (
  code            TEXT PRIMARY KEY,        -- 24 random bytes, base64url
  created_by      INTEGER NOT NULL REFERENCES users(id),
  created_at      TEXT NOT NULL,
  expires_at      TEXT NOT NULL,           -- created_at + 24h
  consumed_by     INTEGER REFERENCES users(id),  -- NULL until used
  consumed_at     TEXT
);

ALTER TABLE records ADD COLUMN user_id INTEGER REFERENCES users(id);
-- Column added nullable for migration safety. Backfilled to the admin's id on first run.
-- New inserts always populate user_id from the session; never from request body.
```

Deliberate choices:
- `email COLLATE NOCASE` gives case-insensitive uniqueness without app-layer normalization.
- 256-bit random session IDs are uniformly random; no JWT.
- `ON DELETE CASCADE` for sessions: deleting a user revokes all their sessions in one statement.
- `messages` table is **not** modified — household chat reads as a shared log; `sender ∈ {'user','bot'}` is sufficient.
- No `households` table — there is one household, implicit.

## 5. Auth flow

### `POST /api/auth/login`
```
req:  { email, password }
work: SELECT user WHERE email=?
      argon2.verify(hash, password)   -- on unknown email, verify against a dummy hash anyway
      if ok: INSERT session; set cookie
resp: 200 { user: { id, email, displayName } }
      Set-Cookie: bo_sid=<sid>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000
fail: 401 { error: "invalid_credentials" }      -- identical for unknown email & bad password
```

### `POST /api/auth/signup`
```
req:  { code, email, password, displayName }
work: SELECT invite WHERE code=? AND consumed_by IS NULL AND expires_at > now
      if invalid: 400 { error: "invalid_invite" }
      INSERT user; UPDATE invites SET consumed_by/consumed_at; INSERT session
resp: 200 { user }, Set-Cookie as above
```

### `POST /api/auth/logout`
```
req:  (cookie only)
work: DELETE session WHERE id=?
resp: 200 { ok: true }; Set-Cookie: bo_sid=; Max-Age=0
```

### `GET /api/auth/me`
```
req:  (cookie only)
work: SELECT session JOIN users; check expires_at > now
resp: 200 { user } | 401
```

### `POST /api/invites`  *(requires auth)*
```
req:  {}
work: INSERT invite { code = randomBase64Url(24), created_by = session.user_id, expires_at = now + 24h }
resp: 200 { code, expiresAt, url: "<BABYONE_ORIGIN>/signup?code=<code>" }
```

### Middleware: `originGuard()` + `requireAuth()`

Two middlewares with distinct responsibilities and mounting orders.

**`originGuard()` — CSRF defense for all `/api/*` writes.** Mounted *before* any route, so it also covers `POST /api/auth/login` and `POST /api/auth/signup` (preventing login-CSRF where an attacker forges a login for the victim's browser into the attacker's account).

```ts
async function originGuard(c, next) {
  if (["POST","PUT","DELETE","PATCH"].includes(c.req.method)) {
    const origin = c.req.header("Origin");
    if (!origin || origin !== process.env.BABYONE_ORIGIN) {
      return c.json({ error: "bad_origin" }, 403);
    }
  }
  await next();
}

app.use("/api/*", originGuard);
```

**`requireAuth()` — session validation for gated routes.** Mounted *after* the open routes (`/api/auth/login`, `/api/auth/signup`, `/api/health`) so they pass through.

```ts
async function requireAuth(c, next) {
  const sid = getCookie(c, "bo_sid");
  if (!sid) return c.json({ error: "unauthenticated" }, 401);

  const row = db.prepare(
    "SELECT s.id, s.user_id, s.expires_at, u.email, u.display_name " +
    "FROM sessions s JOIN users u ON u.id = s.user_id WHERE s.id = ?"
  ).get(sid);

  if (!row || row.expires_at < new Date().toISOString()) {
    return c.json({ error: "unauthenticated" }, 401);
  }
  c.set("user", { id: row.user_id, email: row.email, displayName: row.display_name });
  await next();
}
```

### Security and operational choices
- **Constant-time verify**: `@node-rs/argon2.verify()` is constant-time. The unknown-email path runs a dummy verify so total response time does not reveal whether the email exists.
- **Login rate limit**: in-memory `Map<email, { count, resetAt }>` — 10 attempts per 15 minutes per email → 429.
- **Cookie attributes**: `HttpOnly` (JS cannot read), `Secure` (HTTPS only; off in dev when `NODE_ENV !== 'production'`), `SameSite=Lax`, `Path=/`, `Max-Age=2592000` (30 days).
- **CSRF**: `SameSite=Lax` + `Origin` header equality check on writes.
- **Session expiry**: 30-day fixed. No sliding renewal in V1.
- **Cleanup**: `cleanupExpiredSessions()` runs at server startup; no cron needed at this scale.

## 6. Client changes

### `useMe()` — the auth source of truth
```ts
export const useMe = () =>
  useQuery({
    queryKey: ["me"],
    queryFn: () => api.me(),
    retry: false,
    staleTime: Infinity,
  });
```

Existing queries (`useRecords`, `useMessages`, `useBaby`) gain `enabled: !!me.data`.

### `AuthGate` at App root
```tsx
function App() {
  const me = useMe();
  if (me.isLoading) return <Splash />;
  if (me.error)     return <UnauthenticatedRoutes />;    // /login, /signup
  return <AuthenticatedApp user={me.data} />;            // existing app
}
```

No React Router upgrade — login/signup are two more views guarded by `me.error`, reusing the existing `views.ts` routing.

### New pages
- **`LoginPage.tsx`** — email + password. On success: `queryClient.invalidateQueries({ queryKey: ["me"] })`.
- **`SignupPage.tsx`** — reads `code` from `window.location.search`. Fields: email, display name, password. On success: same invalidate.

### Invite UI
A small `InvitePanel.tsx` in `Sidebar.tsx`. One button — **"Invite caregiver"**:
- Clicks → `POST /api/invites` → shows the URL with a Copy button and "Expires in 24h".
- No list of past invites in V1.

### `api.ts` changes
1. All `fetch` calls add `credentials: "include"`.
2. On any 401, throw a typed `UnauthenticatedError`; a single QueryClient `onError` handler invalidates `["me"]`, which kicks the user back to `LoginPage`.

### "Logged by Calvin" surface
- `GET /api/records` joins `users` and returns each record with `user: { id, displayName }`.
- `RecordModal.tsx` shows "Logged by Calvin · 12 min ago" under the timestamp.
- `POST /api/records` derives `user_id` from the session; the request body's `user_id`, if present, is ignored.

### Logout
"Sign out" button at the bottom of `Sidebar.tsx`. Click → `POST /api/auth/logout` → `queryClient.clear()` → `AuthGate` shows login.

## 7. Migration & first run

### Schema migration
Extend the existing idempotent `CREATE TABLE IF NOT EXISTS` block in `db.ts`. SQLite-safe pattern for the column add:
```ts
const cols = db.prepare("PRAGMA table_info(records)").all() as { name: string }[];
if (!cols.some(c => c.name === "user_id")) {
  db.exec(`ALTER TABLE records ADD COLUMN user_id INTEGER REFERENCES users(id);`);
}
```
No migration framework, no version table. Every change is additive and re-running is a no-op.

### Backfill
After the admin user is created, in `seed.ts`:
```ts
db.prepare("UPDATE records SET user_id = ? WHERE user_id IS NULL").run(adminId);
```
Runs every startup; no-op after first time.

### Bootstrap (first run)
In `seed.ts`, before `serve(...)`:
```
if (users table is empty):
  read BABYONE_ADMIN_EMAIL, BABYONE_ADMIN_PASSWORD, BABYONE_ADMIN_NAME from env
  if any missing:
    console.error("No users in DB and BABYONE_ADMIN_* env vars not set. Set them once, then restart.")
    process.exit(1)
  hash password (argon2id)
  adminId = INSERT user (use lastInsertRowid from better-sqlite3)
  console.log("Created admin user <email>. You can unset BABYONE_ADMIN_* env vars now.")
  backfill: UPDATE records SET user_id = adminId WHERE user_id IS NULL
```

Once seeded, the env vars are ignored on subsequent runs (the `users` table is no longer empty). Operator removes them from `fly secrets` after the first deploy.

### Existing baby profile
`GET /api/baby` and the PUT endpoint added in PR #1 continue working unchanged. Both gain `requireAuth`. No data migration needed.

### Dev environment
`server/.env` gains:
```
BABYONE_ADMIN_EMAIL=you@example.com
BABYONE_ADMIN_PASSWORD=<long random string>
BABYONE_ADMIN_NAME=Calvin
BABYONE_ORIGIN=http://localhost:5173
```
Documented in `README.md` and `DEPLOY.md`.

### Rollback
If something goes wrong post-deploy: redeploy the previous image. The new tables and `user_id` column are harmless to the old code, which ignores them. No DB rollback needed.

## 8. Error handling

| Surface | Failure mode | Response |
|---|---|---|
| Login (bad creds) | invalid email or wrong password | 401 `{ error: "invalid_credentials" }`, constant-time |
| Login (rate-limited) | 11th attempt for same email in 15 min | 429 `{ error: "too_many_attempts" }` |
| Signup (bad invite) | unknown, expired, or consumed code | 400 `{ error: "invalid_invite" }` |
| Signup (email exists) | UNIQUE constraint violation | 400 `{ error: "email_taken" }` |
| Any gated route | no cookie / expired session | 401 `{ error: "unauthenticated" }` |
| Any `/api/*` write (incl. login/signup) | missing or mismatched `Origin` header | 403 `{ error: "bad_origin" }` |
| Bootstrap | empty users + missing env vars | `process.exit(1)` with a clear message |

Client surfaces these as inline form errors (login/signup) or a redirect to login (any 401 on a gated route).

## 9. Testing

Vitest for both workspaces. Server uses `new Database(":memory:")` per test.

### Server tests
- `auth/passwords.test.ts` — hash/verify round-trip; wrong password rejected; verify against junk doesn't throw.
- `auth/sessions.test.ts` — round-trip by id; expired session not returned; revoke removes row.
- `auth/invites.test.ts` — 1000 generated codes are unique; expired invite can't be consumed; double-consume rejected.
- `routes/auth.test.ts` — full integration via `app.request()`:
  - login OK / wrong password / unknown email (same response shape; rough timing equivalence — generous threshold)
  - signup OK / expired invite / consumed invite
  - `/me` with and without cookie
  - logout deletes session row
  - rate limiter: 11th attempt → 429
- `middleware.test.ts` — `originGuard` rejects writes with missing/mismatched `Origin` (including unauthenticated `POST /api/auth/login`); allows GET with missing `Origin`. `requireAuth` rejects no cookie / expired / unknown.
- `db.migration.test.ts` — running migration twice on a populated DB is a no-op; backfill assigns `user_id` correctly.

### Client tests
- `auth/useAuth.test.tsx` — LoginPage renders on `useMe` 401; AuthenticatedApp renders when `useMe` returns a user; `login()` success invalidates `["me"]`; any 401 clears the `["me"]` cache.

### Not tested
- Argon2 itself, Hono cookie helpers, React rendering, Fly deploy behavior.

Estimated implementation: ~25 tests, ~400 lines, half a day.

## 10. Open questions / explicit deferrals

- **Password reset**: No self-service flow in V1 (no email provider). Recovery is a two-step manual process by the admin: (1) delete the user's row from the `users` table (their sessions cascade-delete), (2) generate a fresh invite via the UI for that caregiver to sign up again with the same email. Document this in `README.md`.
- **Sliding session renewal**: not in V1. If 30-day expiry proves annoying, add a `lastUsedAt` column and refresh-on-use in a small follow-up.
- **Origin allowlist for multiple deploy targets**: `BABYONE_ORIGIN` is a single value. If we ever serve from preview deploys, change it to a comma-separated allowlist — not in V1.
